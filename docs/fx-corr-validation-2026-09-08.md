# FX 相関器の精度・速度検証（2026-09-08）

CPU 実装の積算処理を高速化し、位相更新の丸め誤差を抑えた。長基線の三次状位相残差については、過去データで曲率を確認したが、物理的な原因と現行版での解消は未確認である。

基準ソースは `d93b47e28644a7094cfa9cbc4d5c9f29a9781ac9`。測定環境は Core i7-12700H、Rust 1.94.0、既存の `target-cpu=native` と release 設定。

## 変更と精度

- `src/corr_kernel.rs`: 連続した FFT ビンの ACF/XCF 積算を、8本の独立した位相更新で処理する。位相の更新を f64、スペクトルの演算を f32、積分値を f64 とした。空入力と端数ビンも処理する。アーキテクチャ固有の unsafe コードや追加依存はない。
- `src/main.rs`: 通常相関、非連続グリッド、XCF 単独、パルサー積算、phased-array 合成の位相更新も f64 へ揃えた。位相の符号、周波数原点、整数・小数遅延の分割は維持している。
- `src/geom.rs`, `src/model_diag.rs`: 遅延テーブルと診断用グリッドで、捨てていた各局遅延・rate・acceleration を計算しない入口を追加した。従来の全項計算とは、5種類の遅延モデル、3種類の天体方向モデル、短基線・長基線・反転・ゼロ基線、5時刻の計300条件で遅延のビット一致を確認した。

カーネルの回帰テストは、ビンごとに異なる複素入力、正負の位相傾斜、最大524,289ビン、全端数長、既存積分値への加算を、ビンごとに三角関数を直接評価する独立基準と比較する。

`cargo test --offline` は、共有ソースの33テスト×2バイナリと5件の結合テストが通過した。結合テストには phased raw の再相関と3局検証を含む。

## 長基線の位相曲率

既存の次の2ファイルを対応候補として解析した。

- `data/YAMAGU32_HITACH32_2025302081500_yi-corr-gico-v2_c_len2s_add_plot_data.tsv`
- `data/gico3_correct.tsv`

後者はファイル内に絶対epochを持たないため、同一scan・同じ fringe-fit 設定の比較であるかは別途確認が必要。現行ソースから再生成した1時間の比較ではない。

共通する1800点（0〜3598秒）の位相差を unwrap し、時間を [-1,1] に正規化して多項式を最小二乗 fit した結果：

| 除いた多項式 | 残差 RMS [deg] |
|---:|---:|
| 1次 | 555.7973 |
| 2次 | 80.5354 |
| 3次 | 5.4826 |
| 4次 | 0.7585 |
| 5次 | 0.3921 |

3次成分が大きく、さらに高次成分もある。これだけから clock の jerk、座標変換、大気、時刻基準のいずれかを原因と断定することはできない。

現行の通常処理では幾何遅延を1秒ごとに計算し、各フレームの中点で4次まで局所評価する（`YI_GEOM_POLY_ORDER` の既定値4）。scan全体を2次で打ち切る実装ではない。今回の丸め誤差対策を、この1時間の曲率の修正とみなしてはいけない。

既定の幾何モデルは MeanGast と地球速度の一次補正を使う Anchored モデルであり、大気遅延は未モデル化である。比較相手と、EOP、天体座標系、遅延の基準時刻、大気・相対論項を揃えた遅延値の比較が必要になる。精密 VLBI モデルの参照は [IERS Conventions 第11章](https://iers-conventions.obspm.fr/content/chapter11/tn36_c11.pdf)。

曲率解析の再現コード：

```python
import numpy as np

a = np.loadtxt("data/gico3_correct.tsv")
b = np.loadtxt("data/YAMAGU32_HITACH32_2025302081500_yi-corr-gico-v2_c_len2s_add_plot_data.tsv")
t, ia, ib = np.intersect1d(a[:, 0], b[:, 0], return_indices=True)
phase = np.rad2deg(np.unwrap(np.deg2rad(b[ib, 3] - a[ia, 3])))
x = (t - t.mean()) / (np.ptp(t) / 2)
for degree in range(1, 6):
    fit = np.polynomial.polynomial.polyfit(x, phase, degree)
    residual = phase - np.polynomial.polynomial.polyval(x, fit)
    print(degree, np.sqrt(np.mean(residual**2)))
```

超高速化の次段階には GPU 上の復号・batched FFT・位相補正・積算をまとめる余地がある。この環境では RTX 3050 Laptop（4 GiB）を確認したが、今回 GPU backend は実装していない。また、現行の FFT 後のフリンジ回転では FFT 内の位相変化による損失があり、長基線で FFT 長を増やす際には検証が必要になる。[DiFX の原論文 §2.1.2](https://www.atnf.csiro.au/vlbi/correlation/deller.pdf) がこの条件と損失の式を説明している。


## CPU数による違い（追加測定）

上記5.48秒の測定は明示的な --cpu 8。自動設定は物理コア数から1を引くため、このホストでは13計算スレッドになる。全20論理CPUを使う指定は --cpu 20。現行の --cpu は整数引数であり、all という文字列は受け付けない。

同じrelease実行ファイル、同じ5秒のXML/rawを各4回、実行順を変えて比較した。各条件の初回を除く3回の中央値。chunk/pipelineは各CPU数に応じた既定の自動設定。CPU使用率は子プロセスの user+system CPU時間 / 実時間 / 20 で換算した平均であり、他アプリの負荷を含まない。

| 指定 | 計算スレッド | 実時間 [s] | 全20論理CPUに対する平均使用率 |
|---|---:|---:|---:|
| --cpu 8 | 8 | 5.655 | 37.0% |
| 省略（自動） | 13 | 4.800 | 59.2% |
| --cpu 20 | 20 | 4.651 | 82.9% |

自動設定で約59%という結果は、50〜60%の使用率という観測と整合する。13→20スレッドでは使用率の増加に比べて時間短縮は小さく、使用率だけから処理時間が比例して短くなるとは判断できない。各設定の出力スペクトルと時刻も比較した。ログ・CPU時間・出力比較は /tmp/fx-corr-validation/cpu-*.log、cpu-scaling.json、cpu-output-comparison.json に保存。
