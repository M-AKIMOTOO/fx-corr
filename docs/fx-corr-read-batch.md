# Packed input read batching

corr8で単一ファイルのbuffered readは合算851 MiB/s、32 MiBずつ2ファイルを交互に読むPython測定は726 MiB/s、yi-corrは730 MiB/sだった。交互読みの不利は相関計算なしでも再現した。これを踏まえ、ディスク読み込みサイズを計算チャンクから独立させた。ディスクの最大速度やシークだけが原因と断定する測定ではない。

## 使用方法

```bash
yi-corr --sc test.xml --raw raw --cor cor \
  --cpu 15 --chunk-frames 131072 --pipeline-depth 4 --read-batch-mib 256
```

--read-batch-mib は各局のpacked入力バッファ上限MiB（0〜1024）。0は従来通りで、標準値は0。64や256を同じ条件で比較する。初期充填を増やす --buffer-seconds は今回の比較には不要。

局ごとに連続した大きな範囲を読み、そこから整数遅延の補正に必要な範囲だけを既存の計算チャンクへコピーする。遅延・FFT・積分の単位は変わらない。読み込み済み範囲を再利用し、範囲を外れた時に補充する。補充は既存producer上で、キューにあるチャンクの計算と並行する。全体の初期充填待ちは設けないが、最初の両局の読み込みには待ちがある。

範囲は積分sectorの入力末尾までに制限するため、今回の1秒積分・2bit・1.024 GHzでは局あたり約244 MiBで頭打ちになる。指定したMiBの2倍が既存バッファへの追加RAM上限。EOFのゼロ埋めとビット位置を維持する。通常経路は順番に2局を読み、既存 --usb 並行readerにも対応する。I/O用論理CPUは引き続き1つ。

まとめ読み中はチャンクごとのWILLNEEDヒントを省き、既存SEQUENTIAL指定のファイルで読み込む。計算チャンク以上の大きさを要求した時は直接読みへ戻す。チャンクがまとめ読み境界をまたぐ場合は重複範囲を含めて補充するため、読み込む論理バイト数が増える場合がある。

Input read calls の時間には大きな範囲の補充・メモリコピーを含む。表示帯域の分子は計算チャンクへ渡した論理入力量で、物理ディスクの転送量ではない。物理帯域はiostatで確認する。

## 検証

Core i7-12700H/NVMe、5秒実データ、FFT1024、cpu15、chunk131072、pipeline4。旧版、新版0、64、256を順番を入れ替えて各3回実行。以下は中央値。

| 方式 | 実行時間 s | 最大RSS MiB |
|---|---:|---:|
| old-0 | 3.599 | 459.8 |
| new-0 | 3.620 | 460.3 |
| new-64 | 3.759 | 588.6 |
| new-256 | 4.074 | 949.1 |

新版0と旧版はほぼ同じ時間だったが、この環境では64/256 MiBは遅くなった。RAMコピーと初期読み込み待ちが増えるため、すべてのストレージに適するとはいえない。corr8のRAIDでの高速化は未確認であり、標準値を変更していない。

全12実行の相関出力36ファイルはバイト一致。単体45件×2バイナリ、結合6件通過。1/2/4/8bit、非バイト境界の開始位置、重複・後方読み、EOF、空の範囲、並行reader・キャンセル・prefillを検証。両バイナリのreleaseビルド完了。計時結果は /tmp/fx-corr-validation/read-batch/results.json。

長基線の位相残差を修正する変更ではない。
