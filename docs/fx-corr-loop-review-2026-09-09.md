# ループ統合・配列確保の追加調査

RustFFT / RealFFT を継続使用。以下の2案は速度改善を確認できず、ソースを変更前へ戻した。

| 試行 | 変更前 | 変更後 | 判定 |
|---|---:|---:|---|
| 積算と位相更新のループ統合、3200 bins単体中央値 | 15.999 ms | 16.618 ms | 不採用 |
| 通常相関の reduce(init, ...) を reduce_with に変更、全体中央値 | 3.699 s | 3.715 s | 改善未確認、不採用 |

単体測定は1回あたり1200万bin、6回交互に測定し初回除外。統合前後で算術は同じでも、ループ統合が高速化を保証するわけではない。原因となった機械語の詳細は未調査。
全体測定は data/test/yi-corr.xml、5秒分、20スレッド、FFT=8192、前後交互に各4回、初回除外。CPU時間中央値も57.809 → 59.045秒で改善を示さなかった。測定の温度・負荷ばらつきがあるため、わずかな差から一般的な性能優劣は断定しない。

通常相関のACF/XCFは既に同一ループで積算し、FFT scratchと入力・出力配列は仕事単位で確保して複数フレームに再利用している。並列集計のinitもFFT配列を確保するため削除候補だったが、今回の入力では効果を確認できなかった。

合成raw出力の process_frame にはフレームごとの配列確保が残っている。これは通常相関の実測で通らない経路であり、今回の結果から高速化率を推定できない。
